> Carried from `opengame-loading` 1.1.0. Read it when: Get a browser game from link to playable fast, with a near-instant second visit. Covers a first frame that needs no fetch, one loading screen before a menu that means ready, cold visits measured with empty caches, request waves before bytes, budgets that only fall, hashed caching, retries and stall deadlines, a count that reads 100 only at play, the lobby as the loading screen, and textures decoded off the main thread. Use when loading is slow, the bar sticks, or a menu or return visit is slow.


# Loading

A player decides whether to stay before the game has finished downloading. They need a
working title screen with sound in a second or two, an honest count while the world
streams behind it, a menu that answers the moment it shows, and nothing on screen that
is a stand-in for the real thing. A returning player should download nothing. OC (OG
Clash) asked for load speed about 12 times and reached its 15 s target only for returning
players. OS measured a fast boot that turned out to be warm, LC tested first visits on a
fast line while its owner played over a real one, and LC found that the wait was the
main thread more than the megabytes, so the first rules here are the ones that move a
first visit most.

Rules carry five tags; `opengame-quality-bar` explains them and the game codes. Three.js
loaders, compression, Vite and service-worker detail is in
[references/threejs.md](references/threejs.md). An honest count, weighted by the last
visit's timings, is in [helpers/loading-count.mjs](helpers/loading-count.mjs). Frame-time
cost of loading belongs to `opengame-performance`; phone memory and texture caps to
`opengame-mobile`; the visible bar and the press that starts play to `opengame-front-end`.

## Rules

### The title comes first, one boot loading screen comes before the menu, and the menu means ready
- **Invariant:** The first screen a player sees is interactive over key art before the world has downloaded, boot has one loading screen and it comes before the menu, and once the menu shows, starting play answers at once with no second wait.
- **Technique:** Split the download into tiers. The boot tier holds the shell, the key art, the title UI, its music and the input that unlocks audio. The next tier holds what the player will use first (their character, the equipped loadout, the spawn area). The rest loads by need, behind the menu and behind play. The menu waits for each system's first-ready set (what the title and a run's first minute draw), not for everything. Draw the title from a still or a light scene, and swap in the live scene only once it is fully ready. Compile shaders behind the loading screen and menus, not after Play. In a match-based game with many maps, the lobby and countdown are the chosen map's loading screen (the lobby rule below).
- **Reference configuration:** OC's targets: key art on frame one, press-start under 1 s, title under 2 s on a first visit and under 1 s after. OC's 3D title needed the arena (135 MB) and the boss (15 MB) before it could show, and a key-art title estimated at "15x faster first load" was deferred as a 1-2 day build. Loading the arena behind the menus made Play take 0.12-0.15 s. LC's owner: "we jshould just have the lading screen before the main menu... and then main menua nd hitting new run automatically starts game.. no more loading... and optimzie the fuck out of load time so its super fucking fast". LC's title now shows in about 1.0 s with 4.4 MB fetched (it had been 6-7 s and 82.7 MB), the menu waits for each stream's first-ready set, and New run reaches the first frame in 12-23 ms; its 8 s menu at 50 Mbit was never met (15-24 s). OS's owner: "everything nedes to load in under 3s p95 ... (1-2s ideally)" and "how do we get boot to title to a mere seconds? 14s is very high"; it was never met, with boot at 10-14 s and a 22.8 s median from map pick to control.
- **Applies when:** Every game whose world is larger than a few megabytes.
- **Verify:** On a cold cache at the stated bandwidth, record time and bytes to an interactive title, then press Play as soon as the menu shows and record the wait to the first frame of play.

### The first frame is the game's own picture and needs no fetch
- **Invariant:** The first frame the browser paints shows the game's own picture and type, without waiting on any request, and the scene arrives after it at an even pace.
- **Technique:** Inline a tiny blurred still (or a CSS rendering of the first frame) and the title font into the entry document, so first paint needs nothing from the network; swap the full key art and the live content in as they arrive. Publish a first-play budget: requests and bytes to the title, and to the first moment of play. Keep hashed assets immutable and lists revalidated (see the caching rule).
- **Reference configuration:** OH's bare paper showed for 2.9 s before its first picture, 7.3 s at 400 KB/s; a CSS still made the first painted frame instant (0.0 s, 0.1 s at 400 KB/s). Its place paints in 2.2-6 s; the title takes 11 requests and 2.00 MB, and the first note of a linked song 19 requests and 6.86 MB. LC inlines a 19 KB font and a 594 B blurred still.
- **Applies when:** Any game whose scene needs seconds to build.
- **Verify:** Film the page from navigation at 10 fps on a throttled link and measure saturation per frame: no blank frame after the first paint. Count bytes and requests to the title at the server, not only in the browser.

### Cold first visits are fast: few request waves and parallel compiles, measured with empty caches
- **Invariant:** A first-time player reaches the title in seconds, every cold number is measured with an empty browser cache and an empty GPU driver shader cache, and no frame the player sees waits on a compile.
- **Technique:** For each cold run, use a fresh browser profile and point the driver's shader disk cache at a new empty directory, because that cache lives outside the browser profile. Compile boot pipelines in parallel (asynchronous pipeline creation for all of them at once, never one after another), and prewarm heavy variants behind the title, keyed per device and renderer profile. Cut requests before bytes: keep a ledger of which code asks for each file, pack small files into boot packs fetched as the engine starts, and rebuild the boot list from a measured cold boot on every release. When the engine fetches from workers, shape the link at a proxy or the server, because browser network throttling may not reach worker fetches. Time the main thread too: shader graph builds and CPU work can be the whole wait.
- **Reference configuration:** OS's "fresh profile" boot of 5-9 s was warm; truly cold it took 45.6 s, with weapon shaders compiling one after another at 15-18 s each, and compiling them in parallel took it from 42 to 23 s. A prewarm keyed per device and renderer profile cut OS's cold title from 53.2 to 19.9 s. A who-asks ledger took OS's pre-title set from 152 MB in 1,842 requests to 5.40 MB in 180; packs took boot network time from 12-14 s to 8.7 s, and a stale boot list cost 27.2 s against 3.2 s for one rebuilt from a measured cold boot. On OS's link, 22.5 MB arrived in 8-10 s while 80 MB in more files took 12.5-18.7 s: requests, not bytes. OS found that browser throttling skipped its engine's worker fetches. LC: "The wait is the main thread, not the megabytes"; a cached return visit was as slow as a first (11-17 s), and cutting 59 to 39 MB barely moved it.
- **Applies when:** WebGPU or WebGL games with compiled pipelines, and any game that streams many files.
- **Verify:** Back-to-back cold and warm boots, each cold one with a fresh profile and an empty driver cache, print seconds to title for both. A request replay on each release prints requests, bytes and seconds.

### Ship what the runtime requests, listed in a manifest
- **Invariant:** The deployed build contains only files the game requests, and a manifest generated from real runs lists each one with its size and the tier that needs it.
- **Technique:** Log every request during scripted runs through every screen, mode, weapon and device class. Diff the log against the build folder, move unrequested files out, and fail the build when a large file has no entry. Keep a tier and a device class on each manifest entry, and gate the size of each tier. Generate the preload list from a boot with preloading off, so the build writes it rather than a person, and have every capture check it.
- **Reference configuration:** OC's build folder grew to about 6.3 GB in 25,600 files, "mostly files the game never loads"; its deploy worker logged real requests to prune it, and the CDN set came to 3.07 GB. Boot loads grew from 225 MB in 590 files to 833 MB in 6,124 files over a few days, and models from 222 to 490 MB over R74-R77, with no gate to stop them. LC's hand-kept preload list went stale three times in a day and cost about 12 MB, until it was generated from a boot with preloading off.
- **Applies when:** Every game with a build step or an asset pipeline. It matters most when an exporter writes every asset in the project.
- **Verify:** A full scripted run requests every manifest entry, and the build folder holds nothing outside the manifest.

### Bytes before the menu have a budget at a stated bandwidth, and the budget only moves down
- **Invariant:** The bytes needed before the title and the menu, and the time they take on a named connection, are written budgets measured on every build with a cold cache and a throttled network, and no system's share grows without a named decision.
- **Technique:** State the target as time at a bandwidth, convert it to bytes, and gate each build on the bytes each tier actually transfers. Measure with network throttling in a real browser rather than on localhost at full speed, and record the transfer size the browser reports. Keep a record per system that only moves down: each boot records its megabytes before the menu, fails on growth past a small margin, lowers the figure automatically, and raises it only by name from an unflagged boot. Hold each menu code chunk to a fixed compressed byte count, measured on the old and new trees in the same minute, and pay for new bytes by deleting retired flags or moving code into chunks loaded later. Find bytes by source with the source map before trimming by hand.
- **Reference configuration:** OC's target was 15 s or less at 25 Mbps, which is about 47 MB at roughly 3.1 MB/s. Before the title it sent 309 MB in 1,788 files; 291-304 MB took 119.6-123.2 s at 25 Mbps. Compression took that to 181 MB (R164), still about 58 s. LC fails a boot at 3% plus 0.15 MB over a system's record; before the menu LC went from 121.5 MB to 29.66 MB, then to 35.7 MB after multiplayer and new finishes, against a 25 MB target. LC's weapons menu chunk is fixed at 137,501 gzip bytes; raw bytes can fall while compressed bytes rise; rounding 17-digit floats in one JSON register saved 7,711 bytes, and a source map found one misplaced 16,737-byte file after 40 minutes of trims had found 306 bytes.
- **Applies when:** Every web game. Pick the bandwidth with the owner; a phone on mobile data is slower than a desk.
- **Verify:** A cold-cache run under the stated throttle prints bytes transferred and seconds to an interactive title and menu, and fails above budget. A boot that adds a megabyte to one system fails, and the commit message carries the before and after figures.

### Every file is precompressed and typed
- **Invariant:** Every compressible file is served precompressed with the right `Content-Type` and `Content-Encoding`, the server picks the encoding from `Accept-Encoding`, and nothing is compressed twice.
- **Technique:** Write Brotli and gzip siblings at build time and have the host serve them; set types for `.wasm` (`application/wasm`, which streaming compilation needs), `.glb` (`model/gltf-binary`), `.ktx2` (`image/ktx2`) and every custom format. GPU-compressed textures shrink little, so measure each class before spending build time on it.
- **Reference configuration:** OC served its packed model files, asset index and audio with no `Content-Type` and no compression, and its shell ignored a Brotli copy of the wasm (12.6 MB raw against 2.56 MB). Earlier the game binary downloaded uncompressed (10.6 MB instead of 2.1 MB). Measured deflate ratios: GPU textures 1.28x, model files 2.27x, the asset catalog 7.2x. A claim that gzip "saves 20 s" failed audit.
- **Applies when:** Every game served over HTTP. The static host may do this for you; check rather than assume.
- **Verify:** For one file of each type, request it with `Accept-Encoding: br, gzip` and read the response headers; in the network log, the transfer size of each text, wasm and model file is well under its resource size.

### Hashed names and long-lived caching
- **Invariant:** A returning player on an unchanged build downloads only the small entry document, after a deploy downloads only the files that changed, and a page that booted on one build never mixes in files from the next.
- **Technique:** Put a content hash in every asset's file name. Serve hashed files as `Cache-Control: public, max-age=31536000, immutable`, and the entry document as `no-cache` with an ETag. Avoid per-build path prefixes, which change every URL on every deploy. Keep the previous build's hashed files on the host for some hours after a deploy and switch the entry document atomically, so a page booting across a swap still finds its files. A service worker that keeps hashed files in Cache Storage helps where the HTTP cache is evicted.
- **Reference configuration:** OC's content-hash cache (R193) took a returning player from 150 s to 14.7 s. Before it, per-build paths made every deploy a full download. An earlier server rewrite took repeat visits from 714 MB to 5.1 MB. LC's return visit went from 825 requests to 9; pages that booted across a preview swap had 404'd and drew an old model all session, so LC keeps the previous build's files for 3 hours. OS once served 79 newer-build files to an old page; with each publish under its own stamped path, 3,568 of 3,568 requests matched the page's build.
- **Applies when:** Every game that is played more than once or deployed more than once.
- **Verify:** Load, close, load again: the second load transfers only the entry document. Change one asset, deploy, reload: only that file and the entry document transfer. Deploy while a page is mid-boot: it finishes on its own build.

### Fetches retry, and a stalled load is caught by a byte deadline
- **Invariant:** Every fetch can time out and retry, a load that stops receiving bytes is detected and reported, a slow load that is still receiving bytes continues, and a failed load ends on a retry button rather than an automatic page reload.
- **Technique:** Wrap every fetch with an idle timeout reset on each chunk received, retries with backoff and jitter, and a size or hash check on the result. Tell slow from stalled by bytes over time. Show a "slow connection" notice after a stretch with no bytes, keep retrying, and give up only after a long deadline with a button to try again. Cap concurrent requests, and measure the cap against an uncapped cold boot, since a cap can be the stall. Check that a wrapper keeps the platform's own checks, such as range-response handling.
- **Reference configuration:** OC's runtime never retried a failed file, so a load waited on it forever, stuck at 97% (fixed R185). An earlier loader sat at 2% for 74 s after 244 failed requests with no timeout or error path. The page-side guard took 5 revisions over about 2 h, because a first wrapper bypassed range-response checks, and a later version's give-up turned into an "arena stalled" crash. The settings that shipped: the notice only after 20 s with zero bytes, retry with backoff while bytes arrive, and phone requests capped from 128 at a time to 24. OS's cap of 16 reads slowed one load from 5.7 to 24 s ("The biggest recovery and load-time lever is one I caused"). A stall watchdog that frees what a failed load reserved is in `opengame-stability`.
- **Applies when:** Every game that fetches assets after the first document.
- **Verify:** Fail one asset's first three requests (Playwright `page.route` aborting them): the load completes. Fail it every time: the notice appears, the page does not reload, and the error names the file. Throttle to a slow but steady link: no notice.

### The count reads 100 only when play can start, and never goes back
- **Invariant:** The loading count follows bytes received plus weighted non-network work, climbs in small even steps, never goes backward or stands still for long, and reaches 100 only when a run can start; any time-left estimate shown has proved itself accurate.
- **Technique:** Take each file's size from the manifest, count bytes as response chunks arrive, and give shader compiles, environment maps and scene builds their own weights. On a return visit, weight each stage by the seconds it took last time, since time is what the player waits through. Count to the moment play can start, not to the title. Advance the shown number toward the true one at a capped rate so it moves in small steps, and drive it with compositor-only transforms so it keeps moving while shaders compile. Split any stage that holds the number still. Show a time-left estimate only if it held close through whole boots in testing. Hide the count on loads short enough to finish before it would be read. [helpers/loading-count.mjs](helpers/loading-count.mjs) does the counting and reports the longest hold.
- **Reference configuration:** OC's bar stuck at 60% and jumped to 100% ("Baking light" was hard-coded at 60% for about 8 s of work), and stuck at 97% for 20 s before a reload. Fixed, it climbs 1% at a time, holds no number for more than about 0.75 s (0.68-0.73 s measured) and shows only after 0.6 s. A shader warm-up curtain had added 2.5 s of blank screen. The owner asked 3 times. LC's first count read 91% at 0.8 s with play 17-21 s away; weighted by the last visit and counted to play, it reached 100% at 22.1 s with play ready at 21.8 s, rising at most 30 points a second and standing no more than about 1.5-2 s. LC's time-left estimate was 2.8-10.3 s off and was turned off. OS's count hung at 22% on a hard-coded 0.22, first "fixed" with a moving band that measured nothing.
- **Applies when:** Every load the player waits through, first boot and match entry alike.
- **Verify:** Under the stated throttle with a load of 8 s or more, film the count and read it from the pixels every frame: it only rises, holds no value past the cap, and reaches 100 within a frame of play accepting input. The helper's `longestHold()` stays under the cap.

### The menu answers the moment it shows
- **Invariant:** When the menu appears, every row opens its page at once, nothing hidden is still uploading, and the GPU has caught up, so a press on the menu is answered in the same moment.
- **Technique:** Request the menu pages' code chunk when the interface is built, before any world asset, because fetches at the same priority are served first come first served and script cannot be raised above high. Upload nothing hidden before the menu: an engine that builds a geometry's buffers on its first draw will build every hidden mesh in one frame of a warm-up, so trickle them nearest-first in small batches as the GPU answers. Show the menu after the GPU has finished its submitted work (`device.queue.onSubmittedWorkDone()` in WebGPU), with a cap. If a page's code is still late, open its frame at once and fill it on arrival. Find idle stretches of the network line and fill them.
- **Reference configuration:** LC's owner: "buttons are unresponsive on main menu ... and they take like 10s after i hit button for it to open the pag?". The menu pages' 21 KB script was queued behind 170 MB of world fetches; requested when the interface was built, Settings opened in 0.10 s at 5 Mbit instead of 23.0 s, and a late page opens its frame ("OPENING") in 26 ms. LC's 346 hidden litter meshes made 72-134 MB of buffers in one second before the menu; trickled, the menu's wait on a busy card went from 15.7 s to 0.28 s. Showing the menu only after the GPU drained (capped at 12 s) took Enter to a fresh frame from 4.2-9.9 s to 0.54-0.86 s, at a cost of 0.35 s on a quiet card and 1.7-9.6 s on a shared one. At 5 Mbit, 12-13 s of LC's boot had nothing on the line.
- **Applies when:** Every web game that streams after the first screen.
- **Verify:** On a cold boot at a slow link, click every menu row by a real pointer at 1, 3, 6 and 12 s after it appears: each page opens at once. The network log shows the menu chunk before the first world asset.

### What the player sees first is loaded first, and never as a stand-in
- **Invariant:** The equipped weapon, the player's own character and their sounds load at top priority and are resident before the screen that shows them, so no partial, mixed or generic stand-in and no empty hand appears; a complete light copy shows only where `opengame-weapons` allows one, and anything else late shows the previous complete asset or a designed loading state.
- **Technique:** Run fetches through a ranked queue with a few files in flight (measured against an uncapped boot), and order requests by need. Request the chosen loadout from the title as soon as it is chosen, and after the press that starts play let nothing else start while those files fly. Gate screens, purchases and pickups on the asset being ready. Load the equipped weapon's sounds with its model. Keep the old complete model on screen until the new one is fully ready. Stream variety by seconds of play, one texture per task with idle time after it.
- **Reference configuration:** OC's runtime had no priority control, so request order was the only control it had. Weapons the player was given arrived 2.5-7 s late (about 40 s for the heaviest) as mitten hands or black shapes, which spoiled captures in 3 streams and caused a false regression. One lazy-load change put low-poly guns in 6 places; the owner: "dont show the low poly versions anywhere anytime for any weapon anywhere in the game". Gun sounds were silent for 11-16 s, queued behind 35 MB of audio banks. LC keeps at most 4 files in flight (8 in a run); asking for the chosen weapons from the title took Enter to play at 5 Mbit from 3.99-5.32 s to 0.49-0.65 s. OS's rival models waited over 20 s behind a queue full of audio, and backpressure brought 31 posed rivals from 24.4 s to 2.0 s. OS's owner met the opposite failure: "we cant have a situatoinw here not all the gun models load..."; its weapon cards now wait and fade in together (10-25 s became 0.1-0.24 s), and the trade between a complete light model and bare hands is in `opengame-weapons`.
- **Applies when:** Every game with a loadout, a character select or items that appear mid-game.
- **Verify:** On a cold cache under throttle, go straight to play and fire: the first frame of the weapon is the full model and the first shot is heard. Capture every path that hands over an item. The network log shows the loadout first.

### The lobby is the loading screen: count down only on a shown map, and fetch nothing in play
- **Invariant:** In a match-based game, the chosen map streams and compiles during the lobby and countdown, the countdown starts only on a fully shown map and runs straight into play, and the first minute of play downloads nothing new.
- **Technique:** One "shown" gate: the build is done, spawns are validated, pipelines have been ready for two frames, no reads are in flight, and textures are on the GPU. Only after the map is shown, warm the sets the first match draws (killstreak art, rivals' weapons) during the countdown. Slice map building into resumable jobs with a per-frame time budget that guarantees at least one unit of progress a frame and has a hard cap.
- **Reference configuration:** OS's owner: "it says 10 seconds, then 5, 4 and then nothing happens and the game just keeps loading?...". Before the gate, one map showed props over a blue void; after it, ten maps were shown in 1.0-3.1 s. Downloads in the first 60 s of play went from 41.5 MB to 0.0-0.2 MB; warming at the reveal instead had stretched the hold from 21.3 to 41.7 s. A build budget of 6 ms a frame (4 ms on weak machines) took seen frames over 16.7 ms from 24 of 26 to none, and a split without guaranteed progress held the title for 671 s. OS's largest first-match download was 19.6 MB of streak art, now warmed in the countdown. This narrows AW's rule in `opengame-performance`: a countdown may warm, but only what the first match draws, and only once the map is shown.
- **Applies when:** Match-based games with lobbies or countdowns.
- **Verify:** A request log bucketed by phase from a fresh boot through the real lobby shows nothing in the first minute of play. On a throttled run, the countdown waits for the shown gate.

### Images decode off the main thread, and textures ship by role
- **Invariant:** No image decode or texture upload blocks a frame the player sees, and each texture's GPU format is chosen for its role by measurement, so the card holds what the frame draws and no more.
- **Technique:** Decode images with `fetch` and `createImageBitmap` (or `ImageBitmapLoader`), never through an `<img>` element on the main thread. Ship KTX2: ETC1S where colour is seen at a distance, UASTC for normal and data maps unless measurement says ETC1S is enough, and mips stored smallest first so a file's prefix is a smaller valid texture that can be fetched first and sharpened in place. Upload one large texture per task with idle time after it. The measuring is in `opengame-performance`; per-class texture caps for phones are in `opengame-mobile`.
- **Reference configuration:** LC's world textures on the card went from 800.7 MB to 172 MB with ETC1S colour and UASTC data; its in-browser encoder took about 100 s per 2048 map. Decoding through `<img>` had cost 2.5 s of main thread, and a 2048 upload is a 130-650 ms long task. LC's 88 first-set KTX2 files are 22.6 MB whole, 8.0 MB without the top level and 4.1 MB without two, and each prefix transcodes to exactly the bytes of the full file's smaller mips. AW measured ETC1S good enough for its normals at a sixth of UASTC's bytes.
- **Applies when:** Every textured game.
- **Verify:** A boot trace shows no image decode on the main thread and no upload task over the frame budget in play. KTX2 statistics list each texture's codec by role.

### Changing quality never reloads the page
- **Invariant:** Tier and pixel ratio change at runtime without navigation, and a capability probe's result is stored for the next visit instead of applied by reloading.
- **Technique:** Read the stored tier or run a quick probe before creating the renderer (choosing tier and pixel ratio before the first frame is in `opengame-mobile`). Switch passes, resolution and texture sets at runtime. Prewarm only the active tier, and warm another tier when the player picks it.
- **Reference configuration:** An OC probe stored a higher tier 12 s after the title and reloaded the page, which matched the owner's report: "once it got near 100% it just restarted the game". Warming 4 tiers made the last 3-5% of phone loading take 1-3 min.
- **Applies when:** Every game with quality tiers.
- **Verify:** Change the tier in settings during a run: the page fires no `beforeunload`, the run continues, and the log shows one tier prewarmed at boot.

### Loading keeps going in a background tab
- **Invariant:** A player who switches away during the download comes back to a load that kept going.
- **Technique:** Drive loading from fetch promises and message events, not from animation frames. Slice long CPU work with `MessageChannel` or `scheduler.postTask`. Count stall timeouts in visible time only.
- **Reference configuration:** OC's runtime drove loading from its animation-frame loop, so loading halted in hidden tabs. Browsers stop `requestAnimationFrame` in a hidden tab and slow `setTimeout` to about once a second, then once a minute.
- **Applies when:** Every load long enough that a player might switch tabs.
- **Verify:** Start a cold load, switch to another tab for 60 s, return: the progress advanced while hidden, and no stall notice fired.

### A self-hosted build keeps code off the asset path
- **Invariant:** When the game is hosted outside a game platform, heavy assets come from a static host or CDN with no per-request code, with the headers the runtime needs and range requests where the runtime uses them.
- **Technique:** Put the page shell and the heavy assets on separate hosts if one host's limits are smaller than the game. Serve assets as plain static files under content-hash keys. If the game uses threads (`SharedArrayBuffer`), send `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` on the page and `Cross-Origin-Resource-Policy` on the asset host. Check the served build after each deploy (see `opengame-stability`).
- **Reference configuration:** OC split a 106 MB page shell from 3.07 GB of assets on a CDN under per-build paths. A worker function on every asset request billed about 5,000 requests per load. OS put its page on a static host and its assets in a public object bucket under keys of a 12-character content hash plus size, immutable and Brotli, with no code in front, and called a deploy done only when production showed 3,168 requests, 0 failed, 0 console errors and a running match.
- **Applies when:** Games deployed to your own hosting. On OpenGame, `opengame-deploy` covers packaging and the platform serves the files.
- **Verify:** One cold load's request log shows no function invocations for asset files, the isolation headers on the page and the asset responses, and `206` responses where the runtime sends `Range`.
