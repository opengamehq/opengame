> Carried from `opengame-production` 1.1.0. Read it when: Run a browser game build with one or many agents so the owner's notes land in few rounds. Covers the bar set in the first hour, an ask register built from raw messages and ranked by repeats, a lead that never blocks, a ranked gap table, streams that own their paths, publishing as a script, design for loss, a team sized to the model pool and job slots, and updates that show their evidence. Use when a game takes many rounds of owner notes, several agents share it, or fixes never reach builds.


# Production

A game built over many rounds of an owner's feedback loses most of its rounds to
process. OC took about 190 numbered builds in 7 days. About 75 of them never became an
accepted build, about 40 for agent or process reasons, about 22 for engine limits and
about 10 for changes of taste. The owner asked "are you there", "work faster" or "how
are we still on" this round more than 80 times. To run the loop in fewer rounds, front-load the bar,
keep one record of what the owner asked, integrate in one place, and show only what a
build the owner can open proves.

Three later games ran bigger teams and confirmed it. OS shipped about 500 builds in 13
days with 6 to 30 workers and met none of its numeric targets. LC ran up to 14 streams
through about 324 lead sittings in four and a half days. OH built a rhythm game with up
to seven agents in about 70 hours. In all three, infrastructure and process cost more
days than craft: outages took about 37 of LC's 98 hours and about 36 of OH's last 67, and
one blocking question idled 15 OS workers for 7.5 hours. What fixed each failure was a
script that enforced the rule, not the rule written down.

Rules carry five tags; `opengame-quality-bar` explains them and the game codes. The
templates for the register, a brief, a handover, a delivery, a round receipt and a status
update are in [references/templates.md](references/templates.md). The small tools a team
on one machine needs (a slot queue, a sync script, a job start and wait pair, retention, a
preview service, a publish script) are described in [references/team.md](references/team.md).

## The first hour

Settle these with the owner before the first build, and write them into one bar file
that every agent reads. Where the owner has not decided, propose a value and mark it
proposed.

1. **Concept art per screen.** One hero frame at the player's camera for the title,
   each menu, loading, each play area, the HUD, the boss, death and results. A canon
   sheet per character: turnarounds fix identity, scene paintings only composition.
2. **The reference games.** One named shipped game per area, with a saved frame per
   screen at the same camera as the concept (see `opengame-quality-bar`).
3. **Frame rate and devices.** A floor and a typical frame rate for desktop and for
   phones, on named devices and browsers. Mainstream phones, not the oldest. A real
   phone on the desk from the first playable (see `opengame-mobile`).
4. **Budgets.** Bytes and seconds to the title and to play, first visit and returning;
   tab memory; draw calls, lights and enemies on screen; paid generation spend. Check
   the engine's fixed caps (lights, models, particles, handles) against what the
   concept needs now (see `opengame-stability`).
5. **Iconic items.** Anything players will compare with a version they know. Collect
   its reference before anyone models it.
6. **The loop.** The ask register file, the decisions file, the latest playable
   address, the build clock, the status interval, the agent count and which model pools
   they draw on, the heavy-job cap and the compute share with any other project on the
   machine, the path ownership table. Who owns the frame, who owns the renderer, who
   integrates.
7. **Calibration and the owner's path.** Ask the owner to score one comparison sheet 0
   to 10, so the critic can be held to the owner's eye from round one, and write down how
   the owner plays: window size, saved settings, input device, line speed (see
   `opengame-verification`).

In OC each of these was found late. The first-person lens sat at 66.5 degrees against the
concepts' 50-55. A 32-light cap met 218 fire sites. The first written budget came at R79
(360 MB to the title, a 3.5 GB tab) against the owner's ask of a tab under 500 MB. The
latest playable address arrived on day 5, and the first real iPhone crash reports came
after launch. LC's owner gave the standing orders in the first message ("dont ask me any
questions and dont stop until ur done updates every 30 mins"), and OH's lead built the
first playable alone in 65 minutes before splitting the work.

## Rules

### The owner's bar is written down before the first build
- **Invariant:** Concept frames per screen, the reference games, the frame-rate floor and target devices, and the budgets are in one bar file before the first build, and every spec number lives in that file and nowhere else.
- **Technique:** Work through the first-hour list with the owner. Other documents link to the bar file instead of copying its numbers. When the owner raises or changes the bar, update the file that day and add a register row quoting the change. Keep the owner's standing rules in one rules file every brief points at, beside a list of what only the owner can decide.
- **Reference configuration:** OC's kickoff asked for "60fps minimum but up to 120/240fps", and the first written budget came at R79. Boss HP in code was 60,000 against a spec of 400,000; the boss had 3 phases against 4; gate angles changed 3 times across 3 agents. The character canon said 2.2 heads tall where the turnaround measured 2.7. LC wrote the owner's goal ("the most realistic zombies game") at the head of its design document 44 seconds after the message, and into every brief after. OH kept the owner's rules in a shared rules file and an "Only you can decide" list.
- **Applies when:** Every game an owner will review over more than a few rounds.
- **Verify:** Grep the repository for each spec number: it appears in the bar file and in the code that reads it. A new agent answers "what is the phone frame-rate floor" from the file alone.

### Done means it shows in a build the owner can open
- **Invariant:** Nothing is reported to the owner as done until it is seen or heard in a promoted build at the latest playable address, reached through the real menu, with a capture as proof.
- **Technique:** Track each change through written, merged, built, seen in the built round, and promoted. Report only the last two as done and call the rest in progress. New visible work goes in off behind a flag, a default flips only as `opengame-verification` describes under "Main is what the owner plays", and anything worse in play is taken back at once, aloud. Declare a launch build only when every top-priority register row is closed with proof from that build.
- **Reference configuration:** OC's reports of work never seen in a build are in `opengame-verification`. One register sync closed 4 of about 330 rows. "Launch build" was declared at R164, R181, R184, R186, R187, R193 and R196. LC kept a take-back flag for every default and a batch take-back address for the last half hour of defaults; retiring take-backs to save bytes removed the way back.
- **Applies when:** Every report to an owner, every round.
- **Verify:** Every "done" in a status update links a capture from the promoted build that the same update names.

### The ask register is built from the raw messages and ranked by repeats
- **Invariant:** Every owner message maps to a row in one file that stays when any agent's memory is gone: a unique id, the owner's exact words written as a rule for every instance, every date the owner repeated it, the owner's screenshot and conditions, a status only evidence from the exact build can raise, and superseded asks marked "do not revive". Work is ranked by repeat count, and a repeat marks the last fix as failed.
- **Technique:** Have a subagent export every raw owner turn (not docs, commit messages or summaries), build the rows, and re-run after each burst; file a repeat under its existing id. A predecessor's "done" enters as "verify". Pin each note to the owner's screenshot before editing. Send each new note to its owning agent twice: as a row and request file, and as an immediate message quoting the owner. Check a relayed decision against the owner's own message before acting on it. Each confirmed ruling becomes a regression test run before publish. Close the most-repeated rows before taking new scope.
- **Reference configuration:** OC built its register on day 5 from 384 owner messages over several agent threads (179 requirements); "66 of 67 inherited acceptance rows remain open" after about 25 handoffs, one orchestrator told workers the owner had asked "several times" for a plain rifle when the owner had not, and new game modes were added while the frame-rate floor and phone boot were still open. OS's owner asked four times: "There are so many feature requests ... I don't know if, with compaction, you're just losing all those". A catalogue OS built from docs and git gave 153 rows with 12 done; re-reading 423 owner messages gave 128 items, 53 of them "done" claims nobody had checked. At one point 1 of 122 OS asks was verified live while hands had been asked 14 times, invisible walls 10 and spawns 8: "The register was an audit, not a gate." An LC note sent only as a file sat unread for an hour until the owner asked again; acknowledgement then took 1-3 minutes and a ruling 4-10.
- **Applies when:** Every project with more than one agent session or more than a day of owner notes in chat.
- **Verify:** Ten random owner messages each map to a row with a status and evidence, the five most-repeated rows cite current-build evidence, and every open row appears in some running agent's brief.

### The lead never blocks, and standing steers come from the owner's latest words
- **Invariant:** The loop never waits on a person, an owner message reaches the lead within minutes, and no scheduled steer, goal file or brief contradicts the owner's latest explicit instruction.
- **Technique:** Ask in plain text with a recommended default and a deadline, keep working on the safe part, and make reversible calls yourself, saying what you decided. Brief every agent to decide, record and go on. Workers report on completion or a real blocker, and every message that needs no answer ends "no reply needed, continue your round". When the owner changes process, edit the goal file and every scheduled steer in the same turn, quoting the owner, drop queued heartbeats, and say aloud that the newer word overrules the older order. Give a deadline with its fallback in one sentence. Keep scheduled steers slower than the lead's own turns. Never end a turn idle, or only to say you are waiting, while the owner expects continuous work.
- **Reference configuration:** One OS blocking question held the lead 7 h 27 min while 15 workers sat idle; three decisions were asked about 25 times before "u dont need to wait for those decisions on me", and later "Stonasking me qesutions just get it done!". OH's owner, after three idle turn ends: "ok i dont see any work happening?". A 10-minute OS heartbeat repeated an old judge rule 162 times after the owner changed the judges, with 146 copies still queued at handover. Mid-round messages ended three OS workers' rounds until the "no reply needed" line, which was then sent 121 times. LC's lead briefs opened "Do not ask anyone questions and do not wait for an answer: decide, say what you decided, go on", a deadline read "On main within the hour, or take back whichever of tonight's defaults causes it and say so", and 27 LC steers corrected or withdrew an earlier one, each told to the owner the same round.
- **Applies when:** Every lead that runs scheduled steers or workers for an owner who gives live notes.
- **Verify:** Owner messages wait under 2 minutes in the queue, each live steer and brief cites the id of the newest owner instruction it carries out, and a search of live steers for superseded ids finds none.

### A ranked gap table steers the loop, and at launch it becomes a blocker table
- **Invariant:** Each round works the highest-impact open gap game-wide, re-scored from fresh evidence that covers what the judges score, with a cap on attempts per defect. A fault reported or failed twice gets a found cause before a third patch, and when the owner says ship, the table becomes launch blockers with owners and numeric bars.
- **Technique:** Rank gaps by measured point cost and the owner's repeat count. Before a third attempt at one defect, run a diagnostic that names the mesh, shader, light or material drawing it ("Hide one thing at a time" in `opengame-verification`), and write the cause as a test that must reproduce it; after the cap, change approach or park the item and say so. Time-box every chase in jobs ("one more job, then it stands"). Once the last panel's top fixes have landed, judge only what changed. At launch, ship edits nobody has seen right default-off, and production waits for the owner's go.
- **Reference configuration:** Seven OS panels over all 17 maps, run on one-map smokes, scored 1.09-1.21 and each named the same next map, which stayed untouched for 11 h. OS's eight-row launch blocker table (for example, renderer memory growth of 300 MB or less over 45 min) was its clearest steering move. LC mended its spawn fault four times with four flags before the cause on the owner's path was found in 34 minutes; a reload took about ten mends before a fused handle was found, and ten jobs aimed at a muzzle hidden behind the ground stopped only at a two-job cap. The overnight loop on one sub-part and OH's stall rule are in `opengame-quality-bar`.
- **Applies when:** Any hill-climb, overnight loop or launch push.
- **Verify:** The round log shows the ranked table, attempt counters per defect, coverage and per-dimension deltas, and the second report of a fault carries a reproduction and a named cause before any change.

### Batch the owner's feedback and sweep the class
- **Invariant:** Each owner message or play session becomes register rows, each fix covers every instance of its class, and the batch lands in one round instead of one item per round.
- **Technique:** Read the whole batch before starting. Name each item's class and list its members. Split the batch across workers in parallel, integrate it in one round, and reply per item with the round and a capture. When tuning a value the owner disliked, change one variable at a time.
- **Reference configuration:** OC's owner sent a 50-item play-test list on day 2. "we should NOT just be fixing things piecemeal if i send you one example you should be sweeping to make sure by yourself that doesnt exist with anything else of the same thing." The class sweep and OC's gun numbers are in `opengame-quality-bar`. Difficulty swung from "not even killing me" to death in 0.37 s, then settled at 3 hits to down once changes were made one at a time. On day 7: "im not gonna answer any more questions, ive asked for this to be fixed many times". LC's damage, softened for scripted players, went from "the zombeis take so long ot kill u?" to two hits to "it should be 3".
- **Applies when:** Every owner message with more than one item, and every report about one member of a set.
- **Verify:** The reply to a batch lists every item with its round and capture, and each class fix links a sheet of all its members.

### Parallel streams start from a typed contract, own their paths and talk in files
- **Invariant:** Many agents can work in one game at once without breaking each other or the build: a typed contract fixes the seams, each stream owns its paths, and requests and status pass as files anyone can read cold.
- **Technique:** Commit the contract alone first (the shared registry, events and design constants), with stubs so the game boots from the first commit, and get the engine booting before anything else, since nobody can see work before it does. Change the contract by addition only. Keep a path ownership table; a stream edits only its own paths, and a cross-area need goes to that area's owner as a request file stating what, why and the exact interface, closed by a line in the reader's status, never by deleting another stream's file. Put small typed hooks at seams so two agents can build against each other at once. Each stream keeps a status file in a fixed shape the owner can read cold. Prefer building against the contract over waiting.
- **Reference configuration:** LC ran ten streams, later fourteen, in one checkout from a contract committed alone with its stubs; it ended with about 1,900 request files, and other streams' request files were deleted six times before the closing-line rule held. OH split its work into four file-owned passes plus a music studio, with typed hooks such as `loading(share)` and `struck(lane, kind, at)`, because "Broad eleven-item passes were touching many things lightly". An LC cross-stream deadlock left a hand off in 2,003 of 2,003 frames while each side's unit test stubbed the other.
- **Applies when:** Two or more agents in one codebase.
- **Verify:** The main build boots at every commit, no request older than a day is unanswered, and every commit's paths match its stream's row in the ownership table.

### Every change lands through one controlled path, and the shared tree always boots
- **Invariant:** No agent loses, overwrites or commits another agent's unfinished work, nobody rewrites shared history, and anyone can cut a release from the shared tree at any moment because no half-written file, debug probe, missing reference or unseen default reaches it. Changes land through one controlled path: one integrator, or path-named commits through one locked sync tool.
- **Technique:** Choose the landing path on day one. With an integrator, workers deliver small patches against a named base and never edit the integration tree, and the integrator merges, sends back stale-base deliveries and has a different agent review each one. Run one worker per stream and one integration root at a time, with a lock file for the root. With path-owned commits, every commit names its paths and one locked sync script does all pulling and pushing. Either way, never stash, rebase, reset, restore, clean or add everything in a shared tree; check and act in separate calls; diff a shared file before committing it; write files through a temporary file and a rename; land a model re-export with its materials and reference check in one job; run a compile-and-boot check before an edit lands; refuse tagged debug probes in a release; never hard-link snapshots to a tree a build rewrites; keep raw captures out of the repository; and leave repairs to the repository's internals to the lead.
- **Reference configuration:** OC once had 19 workers staging patches while 66 of 67 gates stayed open for 18 h, a stale-base delivery reverted a feature and broke 2 builds, two roots once ran at once for 27 min, and with two teams sharing builds rounds went from about every 15 min to about every 40; from R138 one integrator with a review per delivery ran the loop, every review found a real bug, and film notes reached 10 of 11 shipped in about 36 h. OS's integrator lost about 2 h 45 min to five tree breaks in one evening ("there's no verified safe state to fall back to"); a build read a weapons table while it was being written and every gunsmith showed 0 rifles; 90 snapshots hard-linked to the live cook were rewritten (15.3 GB); 43.5 GB of untracked captures delayed owner messages by 40-60 min. LC took the other path: 2,317 commits in four days from up to 12 agents, zero merges and two index-lock collisions in 36,117 shell calls. When the rule slipped, an LC status file was cut from 276,119 to 9,780 bytes by a script that opened it for writing before reading it, and one lead committed over another's half-written file four times in two hours. OH ran seven agents on one tree with commits by path. "Gates beat instructions: after the second repeat, the lead wrote a check script" (OS).
- **Applies when:** Any build with more than one agent writing code; with three or more on one tree the mechanical gates stop being optional.
- **Verify:** Plant a debug tag, a missing reference and a half-written file: each gate refuses. After a teammate's commit, `git status` still shows your own files, and every merge or commit names its base or its paths.

### Rounds are frozen snapshots on a fixed clock, each with a receipt
- **Invariant:** Each round is built from an instant copy of the integrated source taken at a set time, nobody edits that copy, and the round's receipt says what is in it.
- **Technique:** Cut on a clock agreed with the owner. Take the snapshot as a commit or a copy-on-write clone so the freeze lasts seconds. A change that misses the cut goes in the next round. Write a receipt per round with the source commit, build id, file hashes, the register rows it addresses and its test results. Promote only after a smoke test through the real menu with real input.
- **Reference configuration:** OC agreed a 25-min build clock with sub-minute snapshot freezes, after code freezes of about 20 min per build had slowed the loop. An optic fix landed 9 min after the R91 snapshot and shipped a round late; one cut came 2 h late while private builds held the slots; snapshots failed when source changed during the build at R166, R186 and R189-R190. OC built from frozen source clones from R90, checked 701 artifacts per build from R108, and smoke-tested 60-90 s of normal play before promotion. LC's preview rebuilt from main every 240 s, skipped a failing commit and kept the last good build up; OH built captures and publishes from snapshots of the committed head, so no agent's save could change a running job.
- **Applies when:** Every project with more than a handful of rounds.
- **Verify:** For any promoted round, the receipt's hashes match the served files and the snapshot time is later than every commit in it.

### Publishing is a script: menu-path smoke, soak, exact hash, one publisher
- **Invariant:** The live build moves only through a script that refuses without a passing receipt for that exact snapshot (a smoke through the real menus, a GPU tour and a soak with real play, all before publish), live stays within a round or two of the newest passing build, and a page never mixes files from two publishes.
- **Technique:** A short headless smoke through title, loadout, level pick, lobby and match, whose receipt every agent attaches to every completion report. The publish script hashes the served build from outside, refuses an older round, a dirty tree or a shader error, and has one lock-holding publisher. Cut releases from a source snapshot and serve each publish under its own stamped path, swapping atomically and keeping old hashed files for a few hours for pages still loading. Track judge acceptance apart from publishing, so a bar no build can reach never freezes the preview. A private preview rebuilt from main on a timer is the same script at a smaller size: it builds, boots, skips a failing commit, and leaves the gate on each default ("Main is what the owner plays" in `opengame-verification`); the full smoke and soak still run before anything reaches players. Urgency never skips the gate. The serving half is in `opengame-deploy`.
- **Reference configuration:** An OS direct-load capture looked healthy (5,328 requests) while the gunsmith showed 0 rifles, unnoticed for about 4 h. After "we CANT HAVE THE GAME CRASH EVER!!! ... we need to get to the latest live build asap", an OS build went live 3 minutes later with no evidence and the owner hit a crash and a hang ("I should have held it. I'm sorry."); another passed quick checks and corrupted memory live, so the soak moved before publish, and a later one crashed after about a minute of fighting. OS's smoke took about 90 s. Judge-gating froze OS's preview on one build for 8 h 40 min while candidates moved 28 rounds on. 79 newer-build files once reached an old OS page; stamped paths then pinned 3,568 of 3,568. An atomic swap ended LC's 404s, which had drawn an old model all session.
- **Applies when:** Any live preview or production page an owner or player uses.
- **Verify:** Publish with no receipt, an older round or a dirty tree: the script exits non-zero each time. A publish during a page load leaves 0 mixed files, and the live id equals the newest gated id.

### One latest playable address
- **Invariant:** One permanent address always opens the newest promoted build, every round also keeps its own address, and the sender opens a link before sending it.
- **Technique:** Serve builds from a supervised server on a fixed host and port, started outside any agent session so agent restarts leave it running. Promotion moves the latest address to the new round; older rounds stay at their own paths for comparison and rollback. Label an unpromoted build as untested when you share it. Show the build id on screen in the game.
- **Reference configuration:** OC's owner asked which localhost was the latest about 12 times. A latest address existed only from day 5, and it was then down for 3 days. "Localhost not up" was reported 6 times, agent restarts killed preview servers up to 9 times a day, 20-40 min each, and the stable build was not promoted from R96 to R137. The owner: "every time a new round is ready show me the build link where i can play it". An older OS worktree republished an old build over the shared pointer and live ran 20-30 builds behind ("not lag like 20-30 behind"). LC's preview ran as a supervised service in its own clone, wrote the commit and build time it served, and logged the visiting browser's family so the lead knew when the owner was playing.
- **Applies when:** Every project where the owner plays builds.
- **Verify:** Restart every agent session: the latest address still serves the newest promoted build, and its on-screen build id matches the last receipt.

### Design for loss: agents are disposable, and the status head is the memory
- **Invariant:** Any agent, session, provider or machine can stop at any moment without losing work or decisions, because the work is committed or saved as a patch, each agent's current state sits at the top of its status file where its successor reads first, and a stopped agent is resumed in its own thread from those files rather than replaced blind.
- **Technique:** Commit or save a patch after every job, and keep scripts and state out of temporary directories. Size each agent's job budget to its context (a few jobs, then a handover), since pictures fill context fast. Write the handover at the top of the status file before the context fills: the owner's open notes in the owner's words and where each stands, what is on main and seen (with paths), what is behind which flag and unseen, rulings in their exact words, the next commands, and the agent's own mistakes. While an agent runs, the lead appends its successor's orders to a rulings file, so the next one starts bound by them. After an outage, resume each agent in its own thread with a fixed take-stock (the time, its status head, its own diff, its job marks, recent commits) and decide for each uncommitted change whether it was booted. Run builds and long jobs detached from agent sessions, with deadlines inside the agent host's limits. Amend a brief through the channel that briefed that agent.
- **Reference configuration:** OC had about 25 whole-team usage-limit deaths in about 7 days, each stopping 8-25 agents in the middle of edits with 27-211 dirty files; about 36 of the 160 hours before launch made no progress, and each new wave spent 20-60 min re-auditing. About 37 of LC's 98 hours went to outages (an 8-hour gateway failure, an 8.4-hour machine crash, a 20.7-hour provider stop), and about 36 of OH's last 67. LC ran about 324 lead sittings, a median of 76 minutes; 19% ended because memory filled (81% of reads were pictures), and leads replaced at 520k-900k tokens were productive within the hour. After LC's first outage new leads were started and had to find the old ones' uncommitted work; after the long stop eight were resumed in place and checked their files byte for byte against their last booted job. OH's reboot recovery took about 5 minutes; 257 OS builds came from an uncommitted tree for 73 h until one 683-file checkpoint. OC commits every 20-30 min.
- **Applies when:** Every build that uses agents on metered or shared accounts, or runs longer than a day.
- **Verify:** Stop every agent at a random moment: resumed or fresh agents continue from the files alone, lose no more than the commit interval, and their first status head says what they found.

### Size the team to the model pool and the job slots, and keep the lead out of the workers' failure domain
- **Invariant:** The number of agents running at once stays under what the model pool sustains, no single rate limit or outage stops the lead and every worker together, a dead provider reaches the owner within one update interval, and every status line comes from a check made just before it.
- **Technique:** Cap concurrent agents below the pool's limit, counting nested reviewers and judges, and keep the lead on a different account or pool from its workers. Start agents in staggered waves, since each begins with a heavy read, and tell each to plan and make few, large tool calls. Match workers to the job slots: more workers than slots means queues, not speed. Confirm each launched task actually started, and keep a registry of running agents and the asks each owns; on handover, adopt or cancel the old workers by id. Keep the lead doing hands-on work as well as steering. During an outage, say so in the next update rather than going quiet.
- **Reference configuration:** Ten LC agents at once hit the account-wide rate limit three times in a day, and eleven sessions tripped it where two waves of 6 and 4 did not; LC's cap became eight, with other streams parked and their next orders written. OS's account-wide walls cost about 3 h, 3.5 h and 2 h 45 min; with 20 workers and the lead on one account, a 5-hour limit hit 14 minutes after the lead named the risk, and about 40 heartbeats fired into a dead provider with no alert. OS's later rule was at most 3 workers per account or pool, none on the lead's. On OC, cutting from 20 agents to 17 did not prevent the next usage-limit death, and the root later capped itself at 4. One OS build agent failed 0.26 s after launch while its asks were reported "in flight" overnight, and the lead twice reported "all 14 running" from stale checks. OS's owner: "shouldnt u eb doing owkr here on this machine too?".
- **Applies when:** Any multi-agent run longer than one rate-limit window.
- **Verify:** In a drill, cut one pool partway through a round: the lead still posts, requeues and resumes workers from the repository, and each status line names the time of the check behind it.

### Heavy jobs are slotted, capped, watched to the end, and timed in a quiet window
- **Invariant:** Builds, browsers, captures and renders each hold one slot under a time cap, free it on every exit path, never queue for a slot while holding one, and are watched by their launcher until the result is read; no agent ends a turn with its own job pending, and every performance number comes from a run with no competing heavy work.
- **Technique:** Run heavy jobs through one first-come slot queue whose count someone set from the hardware, with an urgent lane only for a capture that gates a fix to something the owner saw broken, and a quiet lane that drains every slot for timings. One job per agent at a time, with everything for one look in that job. Detach the process, never the watching: wait in your own turn with bounded waits on the job's end mark or receipt. Put timeouts inside the slot, never around the queue, which would count the wait. Reap tagged orphans only after checking their identity. Move builds that need no GPU to CPU machines. Agree the compute share between teams in writing, log competing CPU and GPU load with every perf run and reject runs over the limit, and interleave A/B pairs inside a quiet window, leaving screenshot frames out of timing.
- **Reference configuration:** OC's 16-core machine ran at load averages of 150-361 with 19-36 jobs waiting for 3-6 slots (the cap "was just a default"), free disk fell to 400 MB and killed a run, jobs hit their own timeouts while waiting and the owner's own play lagged, and the game and film teams agreed a 45/45/10 split after more than 40 h of contention, with quiet windows blocking builds for 20-60 min each. LC's four slots for eight leads gave a 41-minute queue and "one look an hour"; one job per lead of at most ten minutes cut the median wait from 279 s to about 100-140 s, though blocking waits were still 20% of lead wall time; LC's quiet lane required a load under 6 and the GPU under 15%. The OS lead sent the stay-in-your-turn correction 41 times in 5 days ("the chain's result reaches no one"); a nested call held a slot idle 83 min, priority queues left normal jobs waiting about 8.5 h, and a timeout wrapped around the queue killed at least five jobs. Moving OS's dev builds to CPU machines took releases from 422-1,057 s to 134 s. The perf-run rejection rule is in `opengame-verification`.
- **Applies when:** Every project running several agents, browsers or renders on one machine.
- **Verify:** Each perf result prints the load and competing CPU and GPU during its run, the queue log shows every wait, and at every turn end the slot status lists no job owned by a finished agent.

### A shared machine is kept by rules: disk lines, retention with receipts, the neighbour's share
- **Invariant:** The project never stops for disk it could have planned for, never deletes evidence someone cites or masters it cannot regenerate, never takes more than its agreed share of a machine another project uses, and never spends money or slots by accident.
- **Technique:** Two disk lines from day one: below the lower one, stop; between them, run only jobs that write little. A retention tool that runs as a dry run by default, keeps anything marked to keep, anything cited and anything recent, keeps the newest few builds per lane, archives captures with checksums before removing them, never follows links or touches source masters, and writes a receipt; never delete by age alone. Measure unique bytes before blaming a writer. Agree a split of slots with any other project in numbers, confirm it by reading that project's own state, and never touch its files. Treat every tool's help flag as untested, and give new tools a dry run first.
- **Reference configuration:** LC's single 12 GB stop line halted streams "again and again" until it became two (stop under 6 GB; between 6 and 12 GB only jobs writing under 1 GB); its cache grew 0.5 TiB a day until a retention tool removed 446 GiB of builds; audio deleted its own masters for space and every check passed while nobody measured the loss. OS's retention scripts deleted cited evidence three times in a day, and running one tool's help flag pruned 14 GB for real; on LC a generation tool's help flag bought 77 voice readings. OH freed 147.9 GiB with a dry-run-first tool, and took two of six slots after the owner's "let the last contact game know it can use 4 and u can use 2", confirmed by reading the other project's count file.
- **Applies when:** Any project on a machine, disk or GPU it shares with other agents or other projects.
- **Verify:** `df` is logged before each heavy job and stays above the lower line across a day, every deletion has a receipt, and the slot count matches the agreed split.

### Reference first for iconic items
- **Invariant:** An item players will compare with something they know (a real weapon or vehicle, a known creature, an item from the creator's own earlier game or spec) is built from measured reference before its first build and judged side by side with it under one camera. Where another studio designed the thing, the reference sets the reads players expect (size, silhouette class, how it handles), and the shipped design, name and files are original.
- **Technique:** Collect a reference model or several orthographic views first. Extract proportions and a materials list, match the reference camera, compare silhouettes from the side, top and back, and write a beat-by-beat spec for how it animates. Keep reference files and trademarked names out of the shipped build, and ship original names.
- **Reference configuration:** OC's wonder weapon went through about 14 builds made from a texture sheet and a 64 px icon, and the owner rejected all of them in one message. The agent: "I built the earlier version without enough reference work." It passed only after the owner sent 6 images and the proportions were measured; the numbers are in `opengame-weapons`.
- **Applies when:** Every item the owner or players will compare with a version they already know.
- **Verify:** A split-view sheet shows reference and build under one camera with the silhouette overlap.

### Owner updates show their evidence, one link and one thing to try
- **Invariant:** The owner hears from the project at an agreed interval, and each update opens with the playable link and the build it serves, says whether the sender booted it, separates what was seen from what was only reported, counted or tested, names one thing to try, and leads with corrections and outages.
- **Technique:** Agree the interval in the first hour. Open with the link, the commit served and its build time, and whether you booted it plain. Then a one-line verdict; what you saw yourself, apart from what you are taking from someone else's report; what is still not right; what is running and what is waiting; take-back flags worth trying; spend. Name one thing to try (a level, a song, a weapon, a setting) and what to look or listen for. Lead with any correction you owe and with any outage. Say every time what nobody could hear, play by hand or watch at speed. Explain jargon, put images in the message, and offer a default with a one-line way out. Skip an update with no news, and never go quiet past the interval.
- **Reference configuration:** OC's owner asked for updates every 10-15 min, about 60% of one transcript was heartbeat boilerplate ("why do you keep sayin gno change?"), and one agent spent about 11 h reporting an old blocked status. LC sent 174 updates on a 30-minute schedule, each opening with the link, the commit served and whether the director had booted it, and told the owner about each of about 44 of its own errors the same round ("A correction I owe you: part of the freeze fix made things worse, and I told you it held."; "You have had no update for about eight hours; that was a failure, not a quiet stretch."). "Nobody has played by hand or heard anything" appeared 53 times. OH's owner: "when u send links pls have expert for the links to try" and "whats a good song i should test now?"; OH kept "Confirmed in captures" apart from "Published, not yet checked by me". OS's owner still asked where things stood at least 8 times.
- **Applies when:** Every project where the owner waits on rounds.
- **Verify:** The update log has no gap longer than the agreed interval, and each update has the link, the build it serves, one thing to try and each claim graded by its evidence.

### The dev log is a typed contract
- **Invariant:** A dev log or progress page the owner reads never shows stale, empty or reworded data without saying so: each field has a type, the owner's words stay exact, and every link resolves.
- **Technique:** Give the log a schema and check it on every change: scores numeric or marked not yet scored, owner requests matched against the raw messages, a media field for every sample, states from a fixed list. Check every link and the preview address on each build. Close a note's state only with evidence from the build. Run the judge panel when the team's own marks say every dimension is close, and say on the page when it has not run.
- **Reference configuration:** LC's board read "This round has no scores yet" for 5 h because the scores were null; 18 voice samples had no slot in the schema and were never linked; the preview link and budget were stale at a machine move; owner requests were reworded; one task was marked done for a rejected effect. At the end 86 of 105 LC quality notes still read "in progress", and the chat updates carried more than the page.
- **Applies when:** Any long build with a progress page, dev log or tracker the owner reads.
- **Verify:** A schema check of the log's data runs on every change and fails on a null score, a reworded quote or a dead link.
