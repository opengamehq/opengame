> Carried from `opengame-stability` 1.1.0. Read it when: Make a browser game crash-free on every device and browser, and prove it. Covers zero crashes as the release bar with recoveries counted, a structural guard per crash class, soak tests, named pools, crash reports that survive reload, a watchdog that tells a slow load from a hang, one composite per frame, no late timer that moves the game, no silent fallback, a booted fallback renderer and the served build checked. Use when the game crashes, freezes, reloads itself or breaks after a deploy.


# Stability

A crash ends the session and usually the player. OC's (OG Clash's) owner asked for zero
crashes about 25 times ("we CANNOT have any crashES EVER on ANY device ANYWHERE").
Crashes took about five days to close from the first ask, among the slowest of any
problem, and stayed open on iPhone after launch. In the end a gate of full sessions on
real devices held, along with crash reports that named the cause and pools that warned
before they were full. OS's owner said it again ("we CANT HAVE THE GAME CRASH EVER!!! any
circumstance.. not an option."), and OS learned that a crash its safety net hides is
still a crash. OH's worst launch fault was not a crash at all: a boot timer that moved
the game out from under a song.

Rules carry five tags; `opengame-quality-bar` explains them and the game codes. Phone
memory kills are in `opengame-mobile`; load stalls and retries in `opengame-loading`;
long-session memory growth in `opengame-performance`; proving a fix ran in
`opengame-verification`.

## Rules

### Zero crashes is the release gate, and a recovery counts as a crash
- **Invariant:** A build ships only when full sessions on every target device and browser end with no crash, freeze, self-reload, recovery or lost input, and a load that times out counts as a failure, not as clean.
- **Technique:** Keep a matrix of device class by browser by flow: cold boot to play, a full match with real input, pause and resume, a returning player with saved settings, a tab switch, a resize or rotation storm, and a GPU device loss. Drive it with real key, mouse and touch input from the title, not a shortcut into the match, and run it the way the owner and players start: through the real menus, under the browser's strict autoplay policy, with every saved setting and cheat they use, at their window shapes (including wider than 16:9), over a real throttled line, beside a second program on the GPU, and with a second run in the same page. Stress each crash class the game has: ammo refills, corpse and debris load, spawn bursts, character and weapon switches. Count every time the safety net recovered the game as a failed session. Treat release-build assertions as live code: guard divisions by zero, negative indices and non-finite values. Count time on both the game clock and the wall clock. Cold means an empty browser cache and an empty GPU driver shader cache (see `opengame-loading`).
- **Reference configuration:** OC's bar: 200 or more consecutive clean sessions, 20 cold boots per device class including a 6x CPU throttle, 60 s of live combat, pause and resume, and a returning player, with load timeouts never counted as clean. Real devices belong in the matrix (`opengame-mobile`). OS's lead: "A crash the net recovers from still counts as a crash to the owner". LC's repeated owner complaints each lived on a path nobody tested (every cheat saved, a return visit, a wider window, a screen recorder on the GPU, strict autoplay), and OH's blank board appeared only under gesture-gated autoplay. An OS capture that loaded straight into a map looked healthy (5,328 requests) while the gunsmith showed 0 rifles for about 4 h. OS's quick smoke is about 90 s through the real menus; an OS build that went live before its soak reached the owner as static, and one that passed a quick soak crashed after about a minute of fighting.
- **Applies when:** Every game anyone outside the team will play.
- **Verify:** The gate prints its matrix with a clean or failed verdict per cell and the session count behind each, recoveries counted as failures; one failed cell blocks the release.

### Each crash class gets a structural guard
- **Invariant:** No asset, map, input or session length can trap, corrupt or exhaust the game, because each crash class found is removed by a guard in the structure rather than by a patch on the one case seen.
- **Technique:** Reproduce on the shipped build, then remove the class: bound retries and free everything a failed load reserved, build large meshes and colliders in pieces, size engine pools for a full match rather than a short test, and count pending shader compiles as progress so a watchdog does not trap a busy load. When a fault moves with content, bisect the content as well as the code, and in an instrumented build trap stores into read-only data to catch a corrupting write where it happens. Run a seeded careless-player fuzzer over every screen (keys, chords, control and right-to-left text, resizes, blur, pointer lock, pads, network drops) that shrinks each finding to its shortest repro. Static or noise from the speakers is memory corruption reaching the output: count it as a crash.
- **Reference configuration:** OS leaked a 256 MB arena per retry over 4,658 retries until it ran out of memory. An allocator returned null and overwrote 102,005 bytes of read-only data, triggered by content; the reasoned fix failed, and a store guard and a data-swap bisect found it. OS's engine pools went from 1,024, 2,048 and 2,048 to 4,096, 16,384 and 4,096 ("My 2-minute switch runs never filled a match"), and its collision is built in chunks of at most 32k triangles with a free-space check. A 10 s watchdog trapped 4K loads with 48 compiles pending. The fuzzer found the Ctrl+X trap the owner had hit, a black screen after a 1x1 resize, and Enter ignored after a key held over a tab switch. OS's "loud static noise ... that really hurt my ears" was a failed allocation writing 5.3 MB of PCM.
- **Applies when:** Browser and wasm games, above all on an engine you cannot patch.
- **Verify:** A soak over every map through the real menus, with read-only and null-page checks after every load: 0 traps and 0 recoveries. Each injected fault recovers once. The fuzzer runs a fixed seed list on every release.

### Soak full runs and count crashes per hundred sessions
- **Invariant:** Stability is measured as a crash count over many complete runs with real input, long enough to reach the late-game states where crashes live, not by one smoke test.
- **Technique:** Run whole matches end to end, many times, on every platform in the matrix, and keep a running crash count per build. Include cold loads as their own count. Make each soak session start from a cold boot and end at results, and log the build id, device and the last screen in every record. In one long soak per release, switch maps repeatedly, make round trips through the menus, inject a trap, a stall, a corrupting write and a GPU loss, and carry on after each. A short smoke test before promotion is a boot check, not a stability claim.
- **Reference configuration:** OC's crashes hit 57-437 s into play (a physics write past the end of an array, read as memory exhaustion for about 40 rounds) and 78-185 s into play (R94-R101), past the 90 s smoke test. After fixes: 0 WebAssembly traps in 300 or more gate sessions (R163-R181), 45 of 45 on the R163 matrix, and 60 of 60 cold loads on each of 3 platforms. That R164 "60/60" ran in Chrome emulation, and the real iPhone crashed within a day of launch. OS's soak bars: zero crashes, pools under 95%, wasm growth under 512 MB per heap, read-only data and the null page unchanged byte for byte after every load, and the last third's frame time within the larger of 2 ms and 15% of the first's; it caught pool asserts, an out-of-memory on the 11th map and the 102,005-byte overwrite.
- **Applies when:** Every game with sessions longer than a minute.
- **Verify:** The release note states sessions run, crashes seen, and cold loads per platform, each tied to the build id, and lists which counts came from real devices.

### Every fixed pool is named, counted live and warned before it is full
- **Invariant:** Every fixed-size table (materials, textures, particles, decals, lights, trails, handles, audio voices, touch slots, instance buffers) has a declared size, a live count and a recorded peak, and warns before it fills; on overflow the game drops the lowest-priority item and logs an error that names the pool.
- **Technique:** Register every pool in one table with its name, size, current count and peak. Show the table in a debug overlay and write it into crash reports. Warn when a pool passes a high share of its size. On overflow in development, throw an error naming the pool and its size; in release, drop the lowest-priority item, log once, and keep running. Where pool sizes are sums written by hand, compute them at build time from the content instead. Size pools from counts taken over a full match. Three.js: read `renderer.info.memory` (geometries, textures) and `renderer.info.programs.length`, keep your own counts for particle, decal and voice pools, and `dispose()` on unload.
- **Reference configuration:** OC hit at least 15 distinct caps: at least 8 crashed or hung a build and at least 4 failed with no message (audio sources, touch buttons, local lights, hide lists). A trail cap of 444, a sum typed by hand, crashed R78 at boot and slipped 25 min of every agent's work by a round. Others: handles at 128 and 512, particle materials in a fixed 512 KB buffer, lights at 280 with overflow a crash, decals 256 of 256, batch instances 192 of 192. A material table of 4,096 filled at about 85 a second because one retry ran 2,432 times. The audio mixer dropped 75% of cues without a word.
- **Applies when:** Every game, and every engine or library with fixed capacities.
- **Verify:** A stress run (maximum enemies, every effect, every weapon) prints the pool table with peaks; each pool pushed past its warning logs its name, and pushed past its size the game keeps running.

### A crash report names what crashed and survives the reload
- **Invariant:** Every crash leaves a record with the error, a symbolised stack, the build id, the device, the screen and the last events before it, written locally before the page dies, uploaded on the next load, and kept until the upload is confirmed and readable by the team.
- **Technique:** Catch `error`, `unhandledrejection`, GPU validation and device-loss events. Keep a ring buffer of recent events (screen changes, spawns, loads, input) and write it with the error to local storage at once. Set a session flag at start and clear it on a clean exit, so the next boot can count a session that died with no error, such as a memory kill. Send a `pagehide` beacon with the outcome. Keep source maps and WebAssembly symbol maps for every release build, private to the team, and keep stacks whole. Give the team a way to read reports back, not only write them.
- **Reference configuration:** OC's WebAssembly stacks had no names (`f1974 -> f1975`) and the fatal text was lost when the module trapped, so agents rebuilt address maps by hand on every build from R98 to R109. Its reset screen "confirms the recovery handler ran; it does not reveal the cause". Local records were deleted after upload, the report endpoint was write-only, and phone memory kills left nothing. The game cut stacks to 160 characters, which hid the caller for 3 rounds; the cap went to 4,000. The owner was asked to paste DevTools expressions before reloading. OC's run-end analytics event later reported crashes through a `pagehide` beacon.
- **Applies when:** Every game played outside the developer's machine.
- **Verify:** Throw from inside one system during a run and reload: the next boot shows or uploads a record whose stack names that function. Kill the tab from the OS: the next boot counts an unclean session.

### The watchdog tells a slow load from a hang
- **Invariant:** A stall detector measures progress (bytes received, load steps done, shader compiles finished, frames ticked), keeps a slow but moving load going, trips only on a real hang, names what it was waiting for, and never reloads the page on its own.
- **Technique:** Give each long job a heartbeat that resets its deadline when it makes progress, and count pending pipeline compiles as progress. Fetch retries and the byte deadline for downloads are in `opengame-loading`. Watch loading by bytes and steps and the main loop by ticks, as separate detectors, and time them on the wall clock, never by summing a clamped frame delta. When one trips, report the guard, the job and its last progress, and show a recovery card. Keep test-script timeouts out of player builds, and make sure a scripted test that runs past its script ends with a clean message, not a crash.
- **Reference configuration:** OC's runtime trapped any wait over 10 s, in release. It fired during loads under machine load and on slow phones, showed a crash card and auto-reloaded: "a big part of last night's iPhone crash and reload near 100% loops". A 12.8 s stall loading boss music ended a run. A test-runner timeout message was taken for a game crash by at least 7 streams. Turning the watchdog off with a URL flag was spotted by the owner in the address bar, and a reviewer noted "Watchdog-off suppresses detection; it does not resolve stalls". It was the most widely reported problem, in 14 notes. OS's 10 s watchdog trapped 4K loads with 48 compiles pending, and an OS heartbeat that summed clamped deltas reloaded a live game running at about 3 fps.
- **Applies when:** Every game with a watchdog, timeout or "loading too long" handler.
- **Verify:** Throttle the network to slow but steady: no trip. Block one request for good: the trip names that file. Busy-wait the main loop: the frame detector names the system. Run a 4K load with a cold shader cache: no trip.

### Recovery never loops and never hides a downgrade
- **Invariant:** After a crash the game recovers to a known screen without reloading itself in a loop, any automatic reload is bounded and returns the player to where they were, and any fallback build or reduced mode it switches to is shown to the player and keeps every feature.
- **Technique:** Count unclean sessions per build. Switch to a fallback only after repeated unclean sessions, for a limited time, keyed to that build so a fixed build starts fresh. Show a notice naming the fallback. Test the fallback as a real build with sound, input and saves. Never call `location.reload()` from an error handler; if a guard must reload, cap how often and restore the same match. Prefer planned refreshes at natural boundaries (between matches) to reset long-lived state over emergency recovery in play.
- **Reference configuration:** OC's fallback pinned after 2 unclean sessions, for 24 h, per build. One fallback build shipped with no sound. OS's canary over read-only memory, checked every 2 s, reloads into the same match at most twice in 5 min; that invisible recovery took 16-66 s against a 15 s target. With planned refreshes at match boundaries, OS ran 30 maps with 0 recoveries.
- **Applies when:** Every game with a crash handler, a fallback bundle or automatic quality steps.
- **Verify:** Force two crashes in a row: the third boot runs the fallback with its notice, plays sound and accepts input; deploy a new build: it starts on the full version. Force a guarded reload mid-match: the player returns to the same match, and a third forced fault in the window does not reload again.

### No late timer moves the game, and nothing falls back without saying so
- **Invariant:** Once play is asked for, boot timers, loaders and deferred callbacks cannot move the game to another mode; a HUD with no playfield cannot persist unnoticed; and a missing or failed file is an error the player reads, never a guessed substitute.
- **Technique:** Have every timer and async callback check that the mode it was set in is still the mode before it acts, and cancel boot timers when play starts. Run a watchdog that restores play if the playfield is missing, and log an error after a short time of HUD with no board or world. Fetch a required data file twice, then say what failed by name. Never replace a missing chart, level or table with generated or default content, and treat a renderer warning that a feature was dropped (a missing attribute, an unsupported format) as an error in development builds.
- **Reference configuration:** OH's boot timer moved the game back to the menus under a song started from a link; the owner hit it twice ("charts not showing? cant even play it?"), and every capture had missed it because captures allowed autoplay. Fixed 81 min after the first report: play is restored within 0.25 s, the framing wait is capped at 6 s, and a song is fetched twice, 700 ms apart, before the player is told which file failed. A missing OH chart had once played a guessed 717 notes for a chart of 403. LC's 4 s press wait, made default from one sitting, sent New run back to the menu on a return visit ("hittin gnew run returned me back to main screen a bit and then eventually started game"). A missing `uv` attribute flattened every LC prop's normal map with nothing but a console warning.
- **Applies when:** Any game with direct links, async boot, deferred timers or data files.
- **Verify:** Reproduce with gesture-gated autoplay and a delayed request, before and after the fix. Return a 503 for a required file: the player reads which file failed. Delay every boot timer past the start of play: the mode never changes.

### One composite reaches the screen per frame
- **Invariant:** Nothing is drawn to the canvas after the full-screen composite, so no frame ever shows a half-built picture or loses a layer.
- **Technique:** Render the world, the playfield and any in-canvas overlays to their own targets, and composite them in one final pass to the canvas. Turn the canvas's own antialias, depth and stencil off, and smooth edges in the shader. Probe it in the page, per frame, over minutes of recorded play.
- **Reference configuration:** OH drew twice to the screen in a frame and lost its board on 4 of 880 frames (49 of 766 with a forced read-back); with one draw to the screen it lost 0 of 3,838 and 0 of 3,786. Judges stepping a clip found it, about 110 min of work. Runs with GL call logging on change the timing and are not evidence either way.
- **Applies when:** WebGL and WebGPU games with post-processing or layers drawn in separate passes.
- **Verify:** An in-page per-frame probe over minutes of recorded play counts frames missing a layer: zero.

### The fallback renderer is booted every time a default changes
- **Invariant:** The fallback path (WebGL 2 under a WebGPU game, or any second render path) is booted and played by an automated gate in the same job as any change to shaders or defaults, the game records which backend it got, and a capture that landed on the fallback without saying so fails.
- **Technique:** A gate forces the fallback, plays a short run, reads the backend inside the page, and fails on any console error, GL error, program link failure, lost context, failed request, or nothing arriving after the menu. Keep the shader's own error lines whole in the log. Add a static check for patterns that compile on one backend and fail on the other. Create the WebGPU device yourself with a bounded number of retries inside a deadline, because some browsers expose `navigator.gpu` before an adapter is ready, then fall back and record why; a missing `navigator.gpu` falls back at once. Three.js: `forceWebGL: true` boots the WebGL 2 backend, and `renderer.backend.isWebGLBackend` reports it.
- **Reference configuration:** LC's fallback drew no scattered props for about 11 hours ("Nothing in the project boots `?webgl`"), because one `min(int, float)` compiled in WGSL and failed to link in GLSL; three.js's GLSL builder emits that shape, so LC greps for an integer first argument to `min` and `max`. LC's gate was proved on the faulty build (`ERROR: 0:406: 'min'`) and on the fix. The fallback ran 44-49 fps against 58-60. Chrome on Linux exposed `navigator.gpu` before its adapter was ready. OC's fallback build once shipped with no sound.
- **Applies when:** Every three.js WebGPU game that ships a fallback, and any game with two render paths.
- **Verify:** Run the gate on a commit with a planted cross-backend fault (it fails) and on the fix (it passes); keep both results.

### The game survives losing the GPU
- **Invariant:** Losing the GPU device or context (a driver reset, a phone reclaiming memory, a long time in the background) leads to a restored game or a one-tap resume card, never a frozen frame.
- **Technique:** Listen for `webglcontextlost` (call `preventDefault()` so a restore can happen) and `webglcontextrestored`, or for WebGPU's `device.lost` promise, then request a new device and rebuild GPU resources from kept source URLs. Pause the simulation while the device is gone. Three.js: `WebGLRenderer` handles the WebGL events itself, so check that your own render targets, data textures and freed CPU copies come back; for `WebGPURenderer`, check your release's device-loss callback and test it.
- **Reference configuration:** OC's loading froze at 80% after a GPU device loss, with no recovery, for two rounds. Its runtime could not recreate the device, so OC showed a tap-to-reload card, and device loss joined the crash matrix. OH launched with WebGL context loss still untested. OS injects a GPU loss in every long soak.
- **Applies when:** Every WebGL and WebGPU game, most of all on phones and laptops that switch GPUs.
- **Verify:** Mid-match, call `WEBGL_lose_context.loseContext()` then `restoreContext()` (or `device.destroy()` on WebGPU): the game comes back or shows the card, and play continues after it.

### Dev commands do not work in public builds
- **Invariant:** A public build has no URL parameter, console hook or key that changes game state, grants items, skips progress or turns off a safety check, and runs that used a dev command never reach a leaderboard.
- **Technique:** Strip dev code at build time behind a build flag. If a dev surface must ship, gate it behind a key the server checks or a stored hash, never a plain parameter. Mark runs that used dev commands and have the leaderboard server reject them. Search the shipped bundle for dev markers as part of the release check. Cheats meant for players are a designed feature, saved and labelled, and the team tests with them on, the way players have them.
- **Reference configuration:** OC's `?commands=` parameter and a global command hook worked on the public host; an agent guessed a URL could hand out a wonder weapon. OC fixed it with a key stored only as a SHA-256 hash. LC ships cheats as a player feature; its owner played with every cheat saved, and a spawn fault that only appeared with all of them on reached the owner four times.
- **Applies when:** Every game with debug commands, cheats or test hooks.
- **Verify:** On the public URL, try every dev parameter and console hook: nothing changes. Grep the shipped files for the dev command names: none match.

### The served build is checked against the tested build after every deploy
- **Invariant:** After each deploy, the files the public URL serves match, by hash, the build that passed the gate, a page never mixes files from two publishes, and the previous good build can be restored in about a minute.
- **Technique:** Write a build receipt listing every file and its hash. After deploy, fetch the entry document and every file, or at least every entry point and binary, from the public URL with caches bypassed, and compare. Make the deploy script stop with an error on a mismatch instead of logging and carrying on. Serve each publish under its own stamped or hashed paths so a page stays on its build, and keep earlier builds on the host so a rollback only points the entry document back. Rebuild every platform variant from the same source on every round. After the hash check, run a cold boot on production through the real menus, never a direct load, to a running match.
- **Reference configuration:** OC's R162 served a binary that did not match its receipt, and "the outer launcher hid that failure". OC checked 701-714 file hashes per round and kept a 1-minute rollback. Its iOS bundle was "last built Oct 17" and shipped stale every round until R160. Production stayed on an old round while a deploy worker tried CDN experiments, and one redeploy did nothing because the script skipped the round being served. OS once served 79 newer-build files to an old page; with stamped paths, 3,568 of 3,568 requests matched. OS calls a deploy done only when production shows its full request count, 0 failed, 0 console errors and a running match.
- **Applies when:** Every self-hosted game. On OpenGame, play the private preview from `opengame-deploy` before calling the release good.
- **Verify:** Deploy, run the check: it passes. Corrupt one file on the host: it fails and names the file. Time a rollback to the previous build. Deploy while a page is mid-boot: it finishes on its own build.
